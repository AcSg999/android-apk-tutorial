# 11 · 上架 Google Play

[返回目录](../README.md) · [上一章](10-app-types.md) · [下一章：国内发布与运营](12-china-and-operations.md)

**上架是另一条发布路径，不是生成 APK 的必要条件。** 本章由读者自行注册账号、提交资料并操作控制台；教程不会代为付款或发布。

规则核验日期：2026-10-20。提交前以账号内提示及官方帮助为准，特别是个人账号测试、目标 API 和身份验证要求。

## 11.1 上架前的决策

- 用户是否能够使用 Google Play？目标地区是否适合该渠道？
- 是否已确定长期包名、开发者主体、签名策略和联系渠道？
- 是否需要同时从官网下载？先解决与 Play App Signing 的签名兼容问题。
- 是否有时间完成封闭测试、填写政策材料、处理审核反馈？
- 是否涉及付费内容、儿童、健康、金融、定位或用户生成内容等额外政策？

“能安装”是技术条件；“允许在市场分发”还取决于产品质量、政策、账号、地区与资料。

## 11.2 注册开发者账号

1. 打开 [Play Console](https://play.google.com/console)，使用自己长期控制的 Google 账号。
2. 按真实情况选择个人或组织类型，填写主体、联系资料并完成身份验证。
3. 按要求完成设备验证、组织证明等当前流程。
4. 确认费用和支付方式后再付款。官方目前列示一次性 **25 美元注册费**，地区、支付条件和额外业务费用应查看 [官方注册说明](https://support.google.com/googleplay/android-developer/answer/6112435)。
5. 开启账号安全保护，限制团队权限；不要共享所有者密码。

不要购买、租借陌生人的开发者账号规避验证。开发者身份与用户看到的公开资料可能影响隐私与长期维护，应在注册时确认。

## 11.3 创建应用与商店资料

控制台创建应用，选择名称、默认语言、应用 / 游戏、免费 / 付费等选项。阅读每项限制，某些价格与身份决策之后不能自由撤销。

准备一份素材包：

| 资料 | 要点 |
| --- | --- |
| 应用名称、简短描述、完整描述 | 描述实际功能，不用不存在的功能作宣传 |
| 应用图标 | 常见要求为 512×512，具体格式大小看当前规范 |
| 置顶大图 / Feature graphic | 常见规格 1024×500，按当前控制台要求 |
| 手机截图 | 使用真实界面，遮掉私人信息，覆盖核心流程 |
| 支持邮箱、网站 | 长期可用、有人处理 |
| 隐私政策 URL | 公开、无需登录、与应用主体及行为一致 |
| 分类、目标用户、国家地区 | 如实选择，别为了少填表误报受众 |

不同设备形态可能要求额外截图，不能只拿手机截图提交 TV 或平板素材。详见 [官方预览素材规范](https://support.google.com/googleplay/android-developer/answer/9866151)。

## 11.4 完成政策声明

常见表单包括 Data safety、广告声明、内容分级、目标受众、应用访问权限、特定权限与行业声明。

Data safety 是向用户说明数据收集、共享和处理的商店表单，不是自动扫描后永远准确的证明。第三方广告、统计、登录、崩溃 SDK 的行为也应计入；不要只看自己写的网络请求。

有登录页面时，按控制台要求提供审核人员可使用的测试账号、登录步骤及必要权限，避免被短信验证码或地区限制卡住。不要提供管理员生产账号或真实用户资料。

应用内允许创建账号时，需要根据当前政策提供账号删除请求路径及相关外部链接；删除账号与单纯退出登录不是同一件事。参考 [账号删除要求](https://support.google.com/googleplay/android-developer/answer/13327111) 和 [用户数据政策](https://support.google.com/googleplay/android-developer/answer/10144311)。

主线离线示例没有账号，但仍须根据实际版本填写隐私与数据表单，不能直接把模板中的所有占位符提交。

## 11.5 生成并上传 AAB

1. 在自己的工程里确认 applicationId、versionCode、targetSdk。
2. 按 [签名章节](07-signing-and-updates.md) 生成 Release AAB，使用预定上传 / 应用签名策略。
3. 新应用通常使用 Android App Bundle 与 Play App Signing；按控制台显示选择并记录签名证书。
4. 上传 `app-release.aab`，查看设备兼容、权限、API 与原生库等检查结果。
5. 不把 APK 改后缀为 AAB，也不把 AAB 发给普通用户直接安装。

对于普通手机 / 平板新应用与更新，截至核验日目标 API 要求是 36 或更高；其他设备类型另有要求，详见 [官方政策](https://developer.android.com/google/play/requirements/target-sdk)。升级 targetSdk 后还要测试行为变化，不只改数字。

包含原生库的应用还应核验 64 位与 16 KB 页大小支持，尤其游戏引擎、Flutter / React Native 插件、音视频和端侧推理 SDK。打包工具新不代表旧 `.so` 自动兼容。

## 11.6 内部测试、封闭测试与正式发布

建议顺序：

1. 内部测试：自己和少量测试者安装 Play 实际分发的版本，验证登录、数据、签名、权限和支付测试。
2. 封闭测试：按目标用户场景收集反馈，保留问题和修复记录。
3. 查看预发布报告，修复闪退、布局、兼容等问题。
4. 符合条件后申请正式发布权限。
5. 创建正式版本，填写发布说明、国家地区与发布设置。
6. 提交审核，等待结果；审核通过后确认是否还需要手动发布。

适用的新个人开发者账号，目前需要至少 **12 名测试者连续加入封闭测试 14 天**，满足条件后再申请正式发布权限；不是“上传就能立刻全量上线”。账号适用范围与具体流程看 [官方测试要求](https://support.google.com/googleplay/android-developer/answer/14151465)。不要沿用旧文章的 20 人要求，也不要把人数达标等同于自动获批。

测试用户要通过受邀测试路径加入；直接发 APK 给朋友安装，通常不等同于完成 Play 要求的封闭测试。

## 11.7 被拒后怎样处理

1. 记录具体政策条款、截图与所审查版本号。
2. 判断是材料缺失、行为不符、权限理由、测试入口还是代码问题。
3. 在真实安装包中修复，更新声明、截图与隐私政策使其一致。
4. 代码变更重新构建并增加 versionCode，再提交。
5. 如认为误判，通过控制台正规渠道说明可复现证据；不要反复原样提交或换号重传。

不承诺审核天数和必过技巧。审核人员需要看到一个完整可用的功能，而非大量占位页面。

## 11.8 发布以后

- 自己通过普通用户路径搜索、下载，验证页面、安装、登录与核心功能。
- 观察 Android vitals 中的崩溃、ANR 和设备问题，收集用户反馈。
- 更新优先使用分阶段发布；首发或某些轨道的可用选项以控制台为准。
- 有故障时停止扩大分发，使用更高 versionCode 提交修复。
- 定期更新目标 API、依赖、Data safety、隐私政策与开发者联系方式。

商店帮你分发，不替你维护服务器、数据库、用户支持或密钥备份。
