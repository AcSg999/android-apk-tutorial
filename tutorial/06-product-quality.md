# 06 · 从能运行到能交给别人

[返回目录](../README.md) · [上一章](05-understand-code.md) · [下一章：签名与更新](07-signing-and-updates.md)

## 6.1 先满足一个完整使用闭环

用没有参与开发的人测试：给他 APK，只说“添加一件事，完成后勾掉，再删掉它”。观察他在哪里犹豫，不在旁边提示操作。

至少检查：第一次打开有说明；空数据有解释；操作后有明确反馈；失败能恢复；删除不会误触；返回、旋转和键盘不破坏操作。

原型可以漂亮，但交付质量取决于正常、空白、加载、失败、权限被拒绝等状态是否都讲得通。

## 6.2 修改名称、图标和版本身份

1. 桌面名称：改 `app/src/main/res/values/strings.xml` 中的 `app_name`。
2. 首页标题：改 MainActivity 中对应文案。
3. 图标：示例提供简单矢量图标。准备正式品牌时，在 Android Studio 用 `New → Image Asset` 创建 Adaptive and Legacy Launcher Icons，选择前景 / 背景，预览不同遮罩。
4. 把 Manifest 的 `android:icon` 改成生成的 `@mipmap/ic_launcher`，按生成结果添加 `roundIcon` 等资源引用。
5. 上架名称、图标、截图、应用内名称保持一致；检查商标与素材授权。

Android 自适应图标会被系统裁成不同形状；不要把小字或关键图案贴边。商店图标与手机启动图标可能有不同尺寸规范，分别按市场要求导出。

## 6.3 本地数据的真实边界

当前主线没有账号、云同步和导出功能。卸载、清除数据、设备丢失，都可能使任务丢失。已保存数据在正常重启和同签名覆盖更新中应保留，但这仍需要真机验证。

如要让别人长期记录重要任务，应优先增加导出 / 导入：

1. 用 Android Storage Access Framework 的文件创建器让用户选择导出位置。
2. 导出带 `schemaVersion` 的 JSON，而不是让用户手动访问内部私有目录。
3. 导入时先解析和验证数量、长度、ID，再提供预览与合并 / 覆盖选择。
4. 覆盖前备份；校验失败不得先清空原数据。
5. 在另一台手机或全新安装中测试导入。

此处是扩展任务，主线尚未实现。文件导出通常不需要申请“访问所有文件”权限；参考 [官方文档与文件访问方案](https://developer.android.com/training/data-storage/shared/documents-files)。

如果数据规模变大，用 Room：先定义实体表与 DAO（数据库访问接口），写查询，再由 Repository 调用。版本升级通过 migration（数据结构迁移）保留旧数据。不要以清库重建代替正式用户的迁移。

## 6.4 最小测试矩阵

| 维度 | 至少测什么 |
| --- | --- |
| 系统版本 | API 26 最低版本、API 36 目标版本、至少一台实际厂商手机 |
| 屏幕与字体 | 小屏、横屏、深色、较大字体 |
| 生命周期 | 切后台、旋转、强制停止、重启设备 |
| 数据边界 | 0 条、1 条、200 条、80 字符、emoji、同名任务 |
| 操作节奏 | 连点添加、快速切换完成、删除取消 |
| 存储 | 保存成功、空间不足时失败提示；不要在主力机故意填满磁盘 |
| 发布 | 新装正式包、旧正式包覆盖更新、浏览器下载后安装 |

测试不是证明“所有情况永远没问题”，而是用有限时间覆盖最可能破坏体验或数据的条件。先覆盖数据不丢、身份正确和主要操作，再考虑精细动画。

仓库单元测试只有业务规则。真实文件保存、失败注入与界面交互如需自动化，可增加 Android instrumentation test；它在设备或模拟器上运行。不要把单元测试通过等同于真机验收。

## 6.5 性能与体积

- 首先观察是否启动缓慢、滑动卡顿、操作阻塞，再用 Android Studio Profiler 定位。
- 不在列表每一行加载原图；图片应用需要压缩、缩略图与缓存。
- 大文件上传要可取消、可重试；不要一次读入全部内存。
- 示例关闭 Release 混淆以减少初学者排障变量；公开产品可以评估启用 R8 代码压缩和资源收缩。
- 开启压缩后必须重新测试，并保留该版本的 `mapping.txt`，供混淆堆栈还原。

包含 C / C++ 或第三方 `.so` 库时，检查 64 位架构和 16 KB 内存页兼容性。只写 Kotlin 并不自动代表全部依赖没有原生库；用 APK Analyzer 检查产物。参见 [Android 官方页大小说明](https://developer.android.com/guide/practices/page-sizes)。

## 6.6 权限越少，第一版越容易交付

权限分两步理解：Manifest 声明“应用可能需要什么”，运行时申请是“用户此刻是否允许”。两者不等价。

- 只在功能实际需要时申请，并先解释用途。
- 用户拒绝后应能返回或使用降级功能。
- 上传图片优先系统 Photo Picker，而非申请读取所有媒体。
- 通知、定位、相机等按照目标系统规则处理。
- 清单权限不只来自自己的 Manifest，第三方 SDK 也可能合并进来；发布前看 Merged Manifest。

主线没有权限请求，联网扩展也仅先添加普通 `INTERNET` 权限。不要把网上的“全权限 Manifest”复制进项目。

## 6.7 隐私说明要描述真实行为

使用 [隐私说明模板](../templates/privacy-policy.md) 作为起点。公开前填入真实主体、联系渠道、日期与数据处理行为。

本示例没有主动接入广告、统计、崩溃收集或网络 SDK，任务写入本机。加入任何 SDK 后，要重新评估数据收集、共享、保存与删除，不能继续照抄“完全不联网”。

隐私政策、首次必要告知、运行时权限、商店 Data safety 表单必须与实际代码一致。政策链接应无需登录即可访问，不能只给一个仓库编辑页面或临时过期链接。

## 6.8 代码和密钥的最小保护

- API 服务商的付费密钥、数据库密码、服务器管理员凭证不要放进 APK。
- 把字符串改名、Base64 编码或启用混淆，都不能把客户端秘密变成真正秘密。
- 签名私钥和密码不要提交 Git、截图发群或写进公开 CI 日志。
- 本地私有目录属于系统隔离，不等于设备被攻破后仍绝对保密；敏感业务需评估加密与威胁模型。
- 只申请所需权限，避免导出内部组件，日志不记录密码、令牌和用户隐私正文。

正式交付前填写 [发布清单](../templates/release-checklist.md)，然后进入签名章节。
