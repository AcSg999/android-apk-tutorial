## 5.1 最少需要的 Kotlin 概念

| 写法 | 含义 | 容易误会的地方 |
| --- | --- | --- |
| `val title = "学习"` | 变量引用不再重新赋值 | 不代表引用指向的对象内部必然不可变 |
| `var title = "学习"` | 引用可以重新赋值 | 使用越多，追踪状态越困难 |
| `String` / `String?` | 不可空字符串 / 可为空字符串 | `?` 是类型约束，不是默认空字符串 |
| `fun add(...)` | 定义函数 | 花括号里才是执行内容 |
| `data class` | 自动生成相等比较、copy 等的数据类型 | 适合表示任务、返回值 |
| `list.map { ... }` | 逐项转换，返回新列表 | 不一定修改原列表 |
| `list.filter { ... }` | 保留条件为真的项 | 筛选不等于删除存储数据 |
| `it` | 单参数 lambda 中参数的默认名 | 嵌套多时用明确名称更清楚 |
| `task.copy(done = true)` | 创建字段改变的新对象 | 不是原对象突然变成另一个值 |
| `suspend fun` | 可以挂起等待的函数 | 不自动保证代码在后台线程运行 |
| `@Composable` | 可参与 Compose 界面构建的函数 | 可能多次执行，不能在里面随意发网络请求 |

Lambda 是一段可以像值一样传递的函数，例如 `{ task -> !task.done }`。`!` 是布尔取反。`==` 比较值是否相等，`=` 是赋值；不要混淆。

详细语言语法可查 [Kotlin 官方入门](https://kotlinlang.org/docs/basic-syntax.html)。不需要学完整门语言后才动手，但每遇到一个陌生写法都应该能解释它的作用。

## 5.2 为什么不把所有逻辑写在按钮里

设想按钮里同时处理校验、读文件、写文件、改 UI。第一次似乎很快；加上第二个入口后，逻辑就容易复制并变得不一致。

本项目把职责分开：

```text
MainActivity / Compose      呈现状态、收集点击
           ↓ 事件
TodoViewModel               调用规则与数据操作、报告错误
           ↓
TodoRepository              读写本机文件
           ↓
Preferences DataStore       持久保存
           ↑ 变化通过 Flow 回到 ViewModel，再到 UI
```

`TodoRules` 放不依赖 Android 的纯规则。这是简化的分层结构，不要求第一天就学依赖注入、模块化或复杂架构名词。

## 5.3 一次添加究竟发生什么

1. 用户输入文字，`input` 状态变化，输入框重新显示。
2. 点击按钮，调用 `vm.add(input)`。
3. ViewModel 标记添加中，避免重复提交。
4. Repository 去掉首尾空白，检查长度与数量限制。
5. DataStore 在一次 `edit` 中读取最新列表，创建 UUID，写入新列表。
6. 保存成功，调用回调清空输入；失败则显示错误，保留输入供重试。
7. DataStore 发出新列表，ViewModel 输出新的 UI 状态。
8. Compose 收到状态，重新显示统计和列表。

UI 不提前宣布“保存成功”。对于写入失败、空间不足或读取异常，这一点比动画效果重要。

## 5.4 状态放在哪里，决定能活多久

| 放置方式 | 普通重绘 | 旋转 / Activity 重建 | 进程死亡后重启 | 卸载 |
| --- | --- | --- | --- | --- |
| 普通局部变量 | 不可靠 | 不保留 | 不保留 | 不保留 |
| `remember` | 保留 | 通常不保留 | 不保留 | 不保留 |
| `rememberSaveable` | 保留 | 可恢复受支持的小状态 | 系统保存并恢复界面状态时可能恢复，不能保证 | 不保留 |
| ViewModel | 保留 | 通常保留 | 不保留 | 不保留 |
| DataStore / Room | 保留 | 保留 | 已成功写入的数据保留 | 通常删除 |

“持久化”就是让数据脱离当前进程的内存，保存到文件或数据库。已经保存的任务依靠 DataStore；输入框草稿与筛选依靠 `rememberSaveable`。因此本示例不承诺强制停止后仍保存未提交草稿。

如你熟悉控制系统，可以把内存状态看作运行中的状态量，把持久化视为落盘的检查点。但并不是每个瞬间的状态都必须持久保存。

## 5.5 协程不是“自动多线程”

协程是一种以顺序写法表达异步等待的机制。等待文件或网络时，让线程有机会处理别的工作；实际在哪个线程执行，取决于所用调度器与 API。

- `viewModelScope.launch`：启动与 ViewModel 生命周期关联的协程。
- DataStore 自身提供异步文件操作，不在按钮内直接同步读写文件。
- 手写阻塞网络请求时，要放进 `Dispatchers.IO` 等合适上下文。
- `CancellationException` 表示协程取消，应该继续抛出，不能当作一般错误吞掉。

后台线程负责耗时工作；更新可观察 UI 状态通常回到合适的主线程上下文。对入门示例，不要一遇到卡顿就到处启动新线程。

## 5.6 Flow 与 StateFlow

`Flow` 可以看成一条随时间发出数据的管道。DataStore 文件变化后，管道给订阅者送出新值。

`StateFlow` 则保留一个当前状态，并允许订阅它的变化。项目的 `uiState` 是 StateFlow，界面不用每秒轮询文件。

`collectAsStateWithLifecycle()` 在合适的生命周期阶段收集状态，减少页面后台时不必要的处理。`WhileSubscribed(5_000)` 表示没有订阅者后，等待 5000 毫秒再停止上游收集，用于平滑短暂页面重建。

这些并不等于跨设备实时同步。它们只描述当前应用进程内的数据变化传播。

## 5.7 为什么列表需要稳定 key

```kotlin
items(visible, key = { it.id }) { task -> /* 显示任务 */ }
```

`visible` 是筛选后的列表；`task.id` 是稳定身份。新任务插到第一项时，原第一项的下标会变，ID 不变。Compose 因而更容易把界面状态关联到正确任务。

UUID 是一种产生近乎不重复标识的方式。它适合本示例的本地任务身份；它不是密码、访问权限或身份认证。

## 5.8 UI 尺寸、键盘和系统栏

- `dp`：随屏幕密度调整的布局单位，不是物理毫米。
- 字体通常使用 `sp`，会响应用户字体缩放；MaterialTheme 已封装常用字体样式。
- `enableEdgeToEdge()`：允许界面绘制到系统栏区域。
- Scaffold 提供内容内边距；`padding(contentPadding)` 避免正文被系统栏覆盖。
- `imePadding()`：给输入法键盘留出空间。
- `LazyColumn`：按可见区域组织可滚动列表，避免把所有行都当作普通 Column 一次铺开。

仍需实际测试横屏、大字体、小屏幕。示例采用手机常规字号布局，极大字体下筛选按钮可能拥挤；可进一步改为 FlowRow 或纵向筛选，并为小屏横屏做可滚动头部。

## 5.9 常见“看起来能运行”的错误

- 只改内存列表，没有落盘：重启后全丢。
- 读取失败就写空列表：可能覆盖原有数据。
- 用显示标题当 ID：两个同名任务互相影响。
- 在 Composable 函数体直接请求网络：每次重组可能重复请求。
- 把长操作放主线程：界面卡住，甚至出现 ANR。ANR 指应用未及时响应系统或用户事件。
- 只看 Debug：Release 的签名、权限、混淆、后端地址不同，可能只有正式包失败。

把“我能解释数据如何流动”作为本章验收，而不只是记住几个类名。
