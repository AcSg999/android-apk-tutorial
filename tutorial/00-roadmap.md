## 0.1 一个 Android 应用到底是什么

把系统拆为四件事：

1. **输入**：用户点按钮、输入文字、拍照，或者服务器返回数据。
2. **状态**：当前有哪些任务、谁已登录、文件存在哪里。
3. **规则**：空任务不能提交、删除需要确认、未登录不能读取私人数据。
4. **输出**：屏幕显示、声音、通知、保存的文件。

应用不是一张静态图片。它是一个不断接收事件、改变状态、重新呈现结果的系统。

先解释下面的符号：`x_t` 表示第 t 次事件前的状态；`u_t` 表示这次输入事件；`f` 是状态转换规则；`g` 是界面呈现规则。`t` 在这里是事件序号，不必是物理时间。

```text
x_(t+1) = f(x_t, u_t)
screen_t = g(x_t)
```

这与你熟悉的系统建模相通。额外要考虑：手机会断网，应用会被系统杀掉，用户会重复点击，文件可能写入失败。因此，状态不能只存在屏幕上的变量里。

## 0.2 从代码到别人手机，中间经过什么

```text
需求与页面 → 源代码与资源 → 编译与打包 → 签名的 APK
                                           ↓
                              上传下载位置 → 用户下载并安装

应用市场路线：源代码 → 签名 AAB / APK → 市场审核 → 商店分发
```

几个首次出现的概念：

| 名词 | 你可以怎样理解 |
| --- | --- |
| 源代码 | 人写的规则，手机不能直接按原样执行 |
| 编译 | 把源代码转换成运行环境能执行的形式 |
| 资源 | 文案、图标、颜色等非业务代码内容 |
| APK | Android 安装包；直接下载分享的主要文件 |
| AAB | 给支持它的市场使用的发布格式，不能当 APK 直接点开安装 |
| 签名 | 用开发者私钥给安装包盖数字印章，供系统判断更新的身份 |
| SDK | 开发工具与接口的集合；Android SDK 包含平台与调试工具 |
| IDE | 集成开发环境；Android Studio 把编辑、构建、调试放在一起 |
| Git / GitHub | Git 保存代码历史；GitHub 托管仓库与发布附件，是两回事 |

有 APK 不代表已经有下载链接；有下载链接不代表已经通过市场审核；商店中的“发布”也不代表服务器已经部署好。

## 0.3 本教程的可验收成果

完成主线后，你应能展示：

- 一台手机上能打开“口袋待办”。
- 输入“学习 Android”，添加后能看到；空白输入不能提交。
- 切换已完成、筛选、删除，结果正确。
- 强制停止应用再打开，已保存任务仍在。
- 断开网络，所有主线功能仍可用。
- 正式签名 APK 能从手机浏览器下载并安装。
- 同一包名、同一签名的新版本能覆盖安装，旧任务保留。
- 保存源码、签名密钥与备份、版本记录和隐私说明。

其中前六项属于主线产品，后两项需要你按发布章节实际执行。市场审核属于外部流程，教材不能保证审核时长或通过结果。

## 0.4 第一个版本故意做小

第一版只做一个离线页面。不加入登录、同步、广告、支付。原因是这些功能各自引入额外系统：账号、数据库、网络、合规和运营。

完整的第一版仍要处理保存失败、输入边界和删除确认。“小”指功能少，不代表忽略真实使用条件。

任务上限为 200 条，每项最多 80 个 UTF-16 代码单元。多数常用中文字符计 1，部分 emoji 计 2 或更多；界面中的“字符”是这个简化上限。示例用小型 DataStore 保存，几万条记录请改用 Room 数据库。

## 0.5 建议学习节奏

| 阶段 | 完成标志 | 遇到问题先看 |
| --- | --- | --- |
| 环境 | `gradlew --version` 正常，SDK 安装完成 | 02、13 |
| 第一轮运行 | 手机上出现首页 | 03 |
| 亲手修改 | 改标题，重新运行能看到变化 | 04 |
| 理解核心 | 能解释添加任务怎样落盘再更新界面 | 05 |
| 发布候选 | 真机回归完成，签名与版本检查完成 | 06、07 |
| 下载交付 | 另一台手机通过链接安装 | 08 |
| 扩展与市场 | 按需求增加功能、填写市场材料 | 09—12 |

初学者给环境和首次构建单独留半天；完整练习通常需要数天。网络、硬件、已有经验差异很大，时间只是安排建议。

准备一个“开发日志”，每次只记录四件事：改了什么、运行了什么、看到什么、下一步是什么。错误截图有用，但更应复制第一条有意义的错误原文。

## 0.6 开始前写一页需求

使用 [需求模板](../templates/product-brief.md)，写出：谁使用、在哪个场景、解决哪个问题、第一版有哪些按钮、每种数据存在哪里、如何判定成功。

例如：“给只想记录当天三件事的自己使用；不注册；数据只在手机；删除前确认；安装与更新不丢数据。”这比“做一个很强大的效率平台”更容易落地。
